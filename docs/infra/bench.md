# Benchmarks

`bench/` holds the GPU benchmarks and `autan-bench`, the harness that times them, records the conditions of the run and gates regressions. Every performance number quoted in a pull request comes from it (`AGENTS.md`, non-negotiable 2).

## Run

Inside the dev image on a DGX Spark, started as [image.md](image.md#use) shows, from the repository root:

```sh
cmake -S bench -B build/bench && cmake --build build/bench
uv sync --project bench --locked
uv run --project bench --locked autan-bench stream --binary build/bench/stream --out results/stream.json
uv run --project bench --locked autan-bench compare results/stream.json bench/baselines/gb10.json
```

## Benchmark any kernel

`autan-bench run` applies the same method to any benchmark binary:

```sh
uv run --project bench --locked autan-bench run --suite codegen --binary build/codegen/bench \
  --precision fp32 --out results/codegen.json -- <binary arguments>
```

The binary prints one JSON object on stdout: `revision` (`commit`, `dirty`, embedded at every build by `bench/cmake/revision.cmake`: in a git checkout whose top level is the source directory, its HEAD and whether tracked files changed; from an export such as an sdist or `git archive`, `-DAUTAN_COMMIT` (40 lowercase hexadecimal characters, as for the runtime); without either the build goes on and records `unknown`, marked dirty, which `autan-bench` refuses to record), `backend`, `runtime_version`, `driver_version`, `device`, a free-form `config`, `verified` (its own check of the results against the specification), and `kernels`, each with `name`, `bytes_per_rep` (useful bytes moved per repetition), `seconds` (one entry per timed sample), and optionally `cells` (cells processed per repetition) and a free-form `params`. Each kernel gives a `<suite>.<kernel>` bandwidth benchmark (GB/s, the numerator of "% of peak") and, with `cells`, a `<suite>.<kernel>.time_per_cell` benchmark (ns per cell per iteration). `autan-bench stream` is `run` with the STREAM binary's arguments.

A binary whose setup is long (reading and renumbering a large mesh) takes `--ready`: `autan-bench run --ready [TIMEOUT_S] ... -- --gate ...` starts it without the GPU lock and waits, at most TIMEOUT_S (default 1800), for the exact line `autan-bench: ready` on its stderr. The binary then waits for one line on its stdin. autan-bench takes the lock, makes its checks (CI priority, frozen campaigns, idle GPU, `--max-load`), writes `go` and samples until the binary prints its JSON. The binary must create no GPU context before `go`: one waiting with a context counts as a compute process, which fails the measurement in progress (`GPU_CONTENDED`) and the idle check. Device setup and uploads therefore come after `go`, under the lock. The result records the setup time in `conditions.setup_outside_lock_s`. A binary that exits or times out before it is ready fails with `BINARY_FAILED`, and the lock is never taken.

### Metal on macOS

On a Mac, `autan-bench run` reads GPU utilisation from the IOAccelerator registry (`ioreg -r -d 1 -c IOAccelerator`, "Device Utilization %") and takes its lock at `~/.autan-gpu.lock`. macOS lists no GPU processes, so the result records `compute_apps_max: null`: contention from another process is not checked there, only utilisation. Clocks, power and temperature need root (`powermetrics`) and are recorded as unknown. That gauge stays at 8–18 % while a bandwidth-bound kernel saturates memory, so on macOS a sample counts as busy above the 5 % idle threshold instead of 50 %; every result records its `busy_threshold_pct` and the utilisation spread during the run. A Metal binary prints `backend: "metal"`, a `device` with `name`, `registry_id` (decimal string), `gpu_cores`, `recommended_max_working_set_bytes`, `memory_bytes` and, from the chip's published specification only, `l2_bytes`; `runtime_version` and `driver_version` encode the macOS version (26.7 → 26070) and `os_version` gives it as text.

## The GPU lock

Every GPU job on a Spark holds `/home/admin/autan-gpu/gpu.lock` while it uses the GPU: one measurement or one test run at a time, at most 10 minutes per hold, at least 2 minutes between two holds by the same agent. `autan-bench` takes it itself. Anything else runs under `bench/lock/autan-gpu-lock`:

```sh
/home/admin/autan-gpu/bin/autan-gpu-lock -m "AGENT: what for" [-w WAIT_S] [-t HOLD_S] -- COMMAND...
/home/admin/autan-gpu/bin/autan-gpu-lock -n -m "AGENT: what for" -- uv run --project bench --locked autan-bench ...
```

`docker/runner/deploy.sh start` installs `bench/lock/autan-gpu-lock` and `autan-gpu-guard` in `/home/admin/autan-gpu/bin/`, which containers see through their mount of the lock's directory. `-n` is only for `autan-bench`, which takes the lock itself and gives CI priority itself: the wrapper waits for CI and for a free lock, then runs it without holding the lock (nesting would deadlock); the `-t` limit then counts from its start, its own lock wait included.

It waits for the lock (at most `-w`, default 3600 s, then exits 75) and runs the command in its own session, without the lock's descriptor. It also keeps the host alive: GB10's GPU allocates from host memory, and a container's `--memory` limit does not bound device allocations (a 2 GiB container allocates and fills 8 GiB with `cudaMalloc`), so the command does not start while `MemAvailable` is below `-f` (default `24G`; `512M`, `0G` for none), and its processes get SIGKILL as soon as `MemAvailable` falls below it, polled every 50 ms, even during the grace of another stop (event `memory`, exit 71). A command that is itself `docker run` gets a `--cidfile`: its container runs outside the session, so whenever the command is stopped (floor, limit, signal) the wrapper runs `docker kill` on it before killing the session, and kills any still running at the end; a `docker run` nested in a shell script is not seen, so run the wrapper as `autan-gpu-lock … -- docker run …` or inside the container. `autan-campaign start --free` applies the same floor to a campaign, frozen or not; both read it through `bench/lock/autan_memfloor.py`. At `-t` seconds (1 to 600, default 600) the session's processes get TERM shortly before the limit and KILL at it (exit 124); a signal to the wrapper does the same (exit 143); a command that cannot start exits 127. Before the lock is released, every process left in the session, and every descendant of one even in a session of its own (checked every 0.5 s), is killed and waited for, so no worker outlives the hold; one stuck in the kernel past SIGKILL is recorded as `leftover` (exit 70). Each event (`wait`, `take`, `release`, `timeout`, `cancelled`, `failed`, `overrun`, `killed`, `memory`, `leftover`) is one line appended to `/home/admin/autan-gpu/holders.log` in a single write: UTC time, event, user (`$AUTAN_AGENT` or the account name), container (`$AUTAN_CONTAINER`, which `docker/spark.sh` sets to `autan-work-<worktree>`, else the host name), seconds waited or held, exit status, the `-m` text and the command, line-breaking characters replaced by spaces. `tail /home/admin/autan-gpu/holders.log` shows who holds the lock. `autan-gpu-guard` runs on each Spark's host (from cron, one instance): every 0.5 s it reads `/proc/locks` and records in `holders.log` every holder of the GPU lock, wrapped or not, with its container and command (the process that took the lock: if it exits while a child keeps the descriptor, the hold is recorded without a container) (`held`, `released`, and `overhold` every 5 minutes past 10 minutes); every 30 s, in a thread that cannot delay the lock's watch, it also lists the GPU's processes outside containers named `autan*`, by process and container name only, never their command lines (`foreign-gpu` when one appears, `foreign-gone` with its duration) and writes the current list to `/home/admin/autan-gpu/foreign-gpu`, from which `bench/ci/gpu-tenants.sh` names, when a GPU job fails, the other team's process that took the GPU (an `::error::` annotation with the host memory still available, a warning when the list is missing, older than 2 minutes or nvidia-smi failed; no retry); it never stops anything. **CI goes first:** `/home/admin/autan-gpu/ci.lock` is held (shared) while a CI job waits for or holds the GPU: by the guard, whenever a process of the runner container is among the lock's holders or waiters, and by the job itself from just before its first GPU step to its end (`bench/ci/priority.sh`, at most the job's timeout), so that CI keeps the GPU between two measurements; and outside CI (`GITHUB_ACTIONS` unset) neither `autan-gpu-lock` nor `autan-bench` takes the GPU lock while `ci.lock` is held; one that took it just as CI announced itself gives it back. A waiting agent records `yield` and keeps its `-w` limit, so it never waits for CI forever, and CI waits at most for the hold in progress (10 minutes). Containers mount the lock's directory read-only and the log file read-write (`docker/spark.sh` does both); the CI runners keep both read-only, so their holds appear in the Actions logs, not in this file. **Main goes before pull requests:** a job on `main` also holds `main.lock` (shared) for as long as `ci.lock`, and a CI job of a pull request does not take the GPU lock while it is held; jobs on `main` run on their own runner process (`bench-main`), so they never queue behind pull requests in GitHub. On the bench Spark, `gpu-bench` builds under the GPU lock as well, so no measurement runs beside a compilation; the other job's light steps (checkout, mesh download, `uv sync`) stay outside it, since they move STREAM by 0.2–0.3 % (5 STREAM runs each on spark-5359, idle and beside a loop of clone, cold `uv sync` and a 263 MB mesh unzip: medians −0.33 % copy, −0.29 % scale, −0.22 % add, −0.30 % triad, against a 2 % threshold declared before measuring).

## Timing method

`autan-bench` applies the same procedure to every benchmark:

1. Takes an exclusive `flock` (recorded with the home directory written `~`) on `/home/admin/autan-gpu/gpu.lock`, waiting as long as needed, or at most `--lock-timeout` seconds (`$AUTAN_BENCH_LOCK_TIMEOUT`), after which it fails with `LOCK_TIMEOUT`; CI waits at most 15 minutes per measurement. Containers mount the lock's directory at the same path, so CI, containers and host shells queue on the same lock. The lock lives outside `/tmp`: there the kernel's `fs.protected_regular` refuses `flock(1)` (which opens with `O_CREAT`) a file owned by another uid, which is every container user.
2. Refuses to start (`GPU_BUSY`) unless, within 5 s, five consecutive `nvidia-smi` samples over one second show no compute process and at most 5 % utilisation (the utilisation counter is a trailing average, so a GPU released a moment ago needs a second to read idle). A GPU that reports no utilisation fails (`NVIDIA_SMI_FAILED`): idleness is measured, never assumed. Another team's job is not something to wait for: rerun later.
3. Records the host's runnable threads (median of 10 samples over 1 s of the kernel's count, `/proc/stat` `procs_running` or `ps -A -M`, the sampler excluded) and its 1-minute load average, before and after the run (`conditions.host_load`). On unified memory (GB10, Apple silicon) other processes' CPU work takes DRAM bandwidth from the GPU, and GPU telemetry does not see it: a Metal STREAM copy measured 169.5 GB/s under a load of ~190 on an M4 Pro, 203 GB/s on a quiet machine. More than 1 runnable thread per CPU is logged as a warning; `--max-load PER_CPU` refuses to run beyond a limit (`HOST_BUSY`). The gate reads runnable threads, not the load average, because the average keeps a [campaign](#cpu-campaigns) frozen a second ago for minutes.
4. Samples SM clock, power, temperature, clock event reasons and the number of compute processes every 200 ms during the run, and fails (`GPU_CONTENDED`) if another process appeared. Clock, power and temperature are summarised over the samples above the busy threshold (50 % with nvidia-smi, 5 % on macOS), so setup and host-side verification do not drag the median to base clock. GB10 reports no memory clock, so none is recorded.
5. Times each repetition with CUDA events around the kernel after warm-up repetitions, and reports the median, quartiles (Hyndman–Fan type 7), IQR and coefficient of variation (CV = standard deviation / mean) of the per-repetition metric.
6. Records provenance with the run-identity names of [results.md](../contracts/results.md) (`solver.commit`, `backend`, `precision`, `devices`). The commit and dirty flag are those the binary was built from (CMake embeds them at every build), so a stale binary cannot borrow a newer checkout's identity; the binary's SHA-256, a host label (`$AUTAN_BENCH_HOST`, which the Spark runners set to the machine name; else a container's short id; else the machine model such as `apple-m4-pro`, never a hostname, which can name a person), the image (`AUTAN_IMAGE`, `AUTAN_IMAGE_REVISION`), the runtime and driver versions and the GPU's name, UUID and properties complete it.

## STREAM and the GB10 peak

`bench/stream/stream.cu` runs the four STREAM kernels (McCalpin 1995) on three FP64 arrays of 2²⁸ elements (2 GiB each, far beyond the 24 MiB L2), 16-byte loads, 256 threads per block, 10 warm-up and 100 timed samples per kernel, each sample the mean of 5 back-to-back launches (about 85 ms). On the shared Sparks, single launches are disturbed by other tenants' CPU traffic on the same LPDDR5x; batching five halves the CV and moves the median by less than 0.5 %. Bytes moved count each array read and each array written once, as STREAM does. Each kernel repeats on unchanged inputs, so the final arrays have exact values and the binary checks them bitwise.

The **GB10 peak bandwidth** is the highest median of the four kernels in `bench/baselines/gb10.json` (`autan-bench peak bench/baselines/gb10.json`). It is the denominator of "% of peak" for every kernel, and it is a measured, achievable peak, below the 273 GB/s of the LPDDR5x datasheet. The baseline pools 5 STREAM runs on spark-5359, 10 minutes apart, each started with the GPU idle and a 1-minute load average of at most 3 (`--max-load 0.15` on 20 CPUs, which then gated the average); `host_load` and `pooled_from` in the file record each run's conditions.

spark-5359 is never quiet: 2 to 5 threads are runnable at any moment (none waiting on I/O), from `dockerd`/`containerd`, Python daemons and about 40 containers of another project (Excalibur: APIs, PostgreSQL, daemons), 47 containers in all, so its load average stays near 2. That background traffic shares the memory with the GPU and is part of the reference: the peak is what a kernel can reach on this machine as it is used, not on an idle one. Never stop or touch those containers.

## CPU campaigns

A long CPU job (a mesh-convergence study, a SU2 comparison) may run on spark-5359 only through `bench/campaign/autan-campaign`, from a host shell:

```sh
bench/campaign/autan-campaign start NAME --dir DIR -- COMMAND...   # DIR is mounted at /work
bench/campaign/autan-campaign status
bench/campaign/autan-campaign stop NAME
```

The campaign runs `COMMAND` in `autan-dev:local` (`--image`), limited to 12 cores (`--cpus`) and 48 GB, at `nice 19` and the lowest CPU weight, without the GPU and without the lock's directory, so it can neither use the GPU nor take the lock. A watcher, detached on the host, starts the container once the GPU lock is free, then reads `/proc/locks` every 100 ms: while any process holds or waits for `/home/admin/autan-gpu/gpu.lock`, it freezes the whole container (`docker pause`, the cgroup v2 freezer), and thaws it when the lock is free. Frozen threads are not runnable and touch no memory. The watcher publishes each campaign's state in `/home/admin/autan-gpu/campaigns/`: `NAME.state` reads `running` before any start or thaw and `frozen` once frozen, and `NAME.heartbeat` is touched at every poll. After taking the lock, `autan-bench` waits up to 10 s for every campaign with a fresh heartbeat to read `frozen`, else fails with `HOST_BUSY`; its load gate (step 3 above) reads runnable threads, which drop as soon as the campaign freezes. The container's first process stops it when the heartbeat is a minute old, so a campaign never outlives its watcher, even one killed with SIGKILL. The watcher removes the campaign if more than 6 threads outside every campaign stay runnable for a minute (each watcher publishes its campaign's cgroup in `campaigns/NAME.cgroup`, so concurrent campaigns do not count against each other) (another project's load: the campaign gives way), when the host's available memory falls below `--free` (default `24G`), and when it stops; every docker call has a 30 s timeout. Its log is `~/autan-campaigns/NAME.log`; results go to `DIR`.

The lane protects measurements that take the lock, which every GPU job must (AGENTS.md). A campaign never takes the lock, and nothing that holds the lock may wait for a campaign. Checked on spark-5359 (2026-11-01): a campaign of 4 spinning threads was frozen 156 ms after the lock was taken (its state read `frozen` after 106 ms in a later run), and runnable threads fell from 9 to 4. A STREAM run with a frozen 12-core memory campaign (12 × `dd bs=64M`) passed `--max-load 0.15`, although the 1-minute average was 10.2 just before, and matched `bench/baselines/gb10.json` within each kernel's CV (copy −1.60 %, scale +0.00 %, add −1.00 %, triad −0.96 %; baseline CV 1.2–1.7 %). The same load left running drops STREAM to 111–126 GB/s, about half. With 9 extra spinning threads outside a campaign, the watcher removed it 65 s later. After the watcher was killed with SIGKILL, the container stopped itself 62 s later.

## Results, baselines and the regression gate

Results follow `bench/src/autan_bench/result.schema.json` (`autan.bench-result/1`); `autan-bench validate` checks a file: the schema, finite numbers only, and statistics that match their samples. `autan-bench compare RESULT BASELINE` judges every baseline benchmark. Its median is a **regression** when it is more than 5 % worse (exactly 5 % passes) *and* the 95 % confidence intervals of the two medians are disjoint (percentile bootstrap, 2000 resamples, fixed seed, so the verdict is reproducible); more than 5 % worse with overlapping intervals is **inconclusive**: the shift is within the noise. It exits 1 on a regression, 3 when only inconclusive verdicts remain, 2 when the files cannot be compared (different GPU, configuration or metric, missing benchmark). In CI, `bench/ci/gate.sh` measures once more whenever a median is more than 5 % worse, and the second measurement decides: a regression there fails, an inconclusive verdict there is a warning. `autan-bench baseline RESULT --out bench/baselines/<gpu>.json` promotes a result only if its binary was built from a clean checkout, it records its environment (the image digest; on macOS, where Metal runs without a container, the OS version), each STREAM array is at least 4 × L2, and every benchmark has a CV below 2 %.

`--select PATTERN` (repeatable glob) keeps only the tracked benchmarks in the baseline; `compare` then gates those and ignores the others.

### When `gpu-bench` runs

The workflow starts for every pull request and every push to `main`, but its `mesh` and `bench` jobs run only when something that is measured, or builds what is measured, changed: `runtime/`, `codegen/`, `kernels/`, `physics/`, `solvers/`, `core/`, `io/` (readers fix the face and cell order of the measured mesh), the image (`docker/dev/`), the measurement method (`bench/src/`, the harness's `pyproject.toml` and `uv.lock`, `bench/stream/`, `bench/cmake/`, `bench/baselines/`, the gate `bench/ci/gate.sh`), any `CMakeLists.txt` or `.cmake` file, the mesh generator (`vv/src/autan_vv/meshes/`) or the workflow itself (`bench/ci/changes.sh` decides). When only the harness's tests, other CI scripts or tools changed (`bench/tests/`, `bench/ci/`, `bench/lock/`, `bench/campaign/`, `docker/runner/`), the same required `bench` job runs the harness's GPU tests and the image smoke test on the `tests` runner instead, under the same lock, and the bench Spark is left for measurements. A change to the gate's thresholds is stated in its pull request. A pull request is judged on its own change, the difference between GitHub's merge commit and its first parent (the current base), so files that reached the branch by merging `main` do not count; a push to `main` is judged on the difference with the last commit of `main` whose `bench` job ran and passed (`bench/ci/last-measured.sh`), because runs on `main` queue in one concurrency group and GitHub cancels a pending run when a newer one arrives, so the newest run must also cover what a cancelled run carried; when the API cannot tell, the push is measured. Otherwise they are reported as skipped, which satisfies the required check, so a Python, documentation or UI change never waits for the GPU. Draft pull requests are not measured: their jobs are skipped in `gpu-bench`, `gpu-tests` and `gpu-hip`, which satisfies the merge gate, and marking the pull request ready for review starts them. To measure a branch before that, dispatch the workflow on it, which always measures: `gh workflow run gpu-bench.yml --ref <branch>` (likewise `gpu-tests.yml`).

### Bisecting a regression of main

When a run on `main` confirms a regression of the tracked loops (`bench/ci/gate.sh` exits 1 after its rerun) on a machine whose STREAM check passed, the same job finds the commit, on the same Spark and with the same protocol, before the runner takes another job. `bench/ci/bisect.py` searches the first-parent commits between the last commit of `main` that passed (`bench/ci/last-measured.sh`, looked up by the `changes` job) and the failing one: about log2(k) probes for k commits, at most 64 commits and 8 probes. Each probe (`bench/ci/measure-point.sh`) builds that commit's loop benchmark in a separate worktree, checks the machine with STREAM against `gb10.json` (three tries; a machine that fails is never interpreted) and gates the loops as the detection did; every measurement takes and releases the GPU lock on its own. A culprit is named only if it also regresses from its parent on the tracked loops (`bench/ci/compare-points.sh`); otherwise the shift is spread over several commits and none is blamed. A probe that fails for any other reason (a GPU lock not taken in time, a build error) stops the bisection without a verdict. The `report-regression` job, on a GitHub-hosted runner and with the only write permissions of the workflow, opens an issue labelled `perf-regression` (culprit, spread, or where the bisection stopped) and comments on the culprit's pull request with its ns per cell before and after. A real probe on spark-5359 (main at a0ab8e3) built, passed STREAM and gated the loops in 372 s.

### Performance history of main

After every run that measures `main` and uploads results (passed, or failed and bisected), the `history` job rebuilds the history from each measured run's artifact still kept by GitHub (`bench/history/fetch.sh`), bisection probes included, and uploads `perf-history`: `history.json` (one record per commit, its latest measurement: medians, CV, % of the GB10 peak, host, image), `history.csv` (one row per commit and benchmark) and `history.html` (one chart per tracked benchmark; red points are commits a bisection blamed). Commits follow main's first-parent order, not measurement time. `bench/history/history.py ARTIFACTS --order FILE --baselines bench/baselines --out DIR`, with FILE from `git rev-list --first-parent --reverse origin/main`, builds the same files from downloaded artifacts. The charts show at least ±5 % around the data, so run-to-run noise does not read as a trend.

### Tracked generated loops

`gpu-bench` also builds `autan_loop_bench` (`codegen/`), runs it on the hexahedral mesh n = 128 (2.1 M cells, generated by `autan-vv` on a GitHub-hosted runner because Gmsh has no aarch64 wheel, and cached under the hash of what `autan-vv meshes` runs (`vv/src/autan_vv/meshes/`, `oracles/`, `cli.py`, `errors.py`, `__init__.py`, `vv/pyproject.toml`, `vv/uv.lock`, `vv/.python-version`), so it is generated again only when the generator or its dependencies change; a pull request reads its base branch's cache, which `mesh-cache.yml` fills on every such change to `main`) in `fp32` with RCM order, and compares against `bench/baselines/gb10-codegen-hex-n128-fp32.json`. The tracked loops are the face-loop advection with atomics and with warp aggregation, and the LSQ gradient with bounds, in bandwidth and time per cell. Their samples drift by 2–4 % (CV) on the shared Spark whatever the batching, so their baseline is promoted with `--max-cv 0.04`; run-to-run medians stayed within 3.5 %. The false-positive rate of the gate on identical code is in the next section. The other strategies (colouring, store-gather, gather-recompute, Roe variants) are measured and uploaded but not gated.

### False positives and sensitivity

Measured on spark-5359 on 2026-11-01: 11 consecutive runs of identical code (STREAM, and the generated loops on hex n = 128 in `fp32`), run 0 as baseline, runs 1–10 compared with it, while other jobs queued on the lock.

| | STREAM (4 benchmarks) | Tracked loops (6 benchmarks) |
|---|---|---|
| Largest spread of one benchmark's median over the 11 runs | 4.3 % | 6.2 % |
| 95 % bootstrap interval of a median, as a share of it | 0.6–1.6 % | 0.6–4.3 % |
| Identical code flagged at 5 %, one run | 0 / 40 | 0 / 60 |
| Identical code flagged at 3 %, one run / confirmed by a second run | 1 / 40 → 0 | 6 / 60 → 0 |
| 6 % regression (injected) detected at 5 %, one run / confirmed | 40 / 40 → 40 | 47 / 60 → 40 |
| 10 % regression (injected) detected at 5 %, one run | 40 / 40 | 60 / 60 |

The noise is a drift between runs (other tenants' traffic on the shared memory), not jitter within a run: intervals computed within one run are narrow and flagged exactly the same comparisons as the plain median rule. A second, independent run is what removes false positives, so the gate confirms every failure by rerunning. The price is sensitivity near the threshold: on the generated loops a true 6 % loss is caught two times out of three, a 10 % loss always.

A baseline pooled from 5 runs (`autan-bench baseline R1 … R5 --min-runs 5`: the samples of all runs, statistics recomputed, `pooled_from` listing the runs) gives a reference that does not depend on one lucky or unlucky run. On the same data (runs 0–4 pooled, runs 5–10 compared) it did not detect small regressions better: a 6 % loss on the generated loops was confirmed 20 times out of 36 against 24 with run 0 alone, an 8 % loss 34 out of 36 with either, and identical code was never flagged. The limit is the drift of the run being judged; reliable detection starts near 8 % on these loops and below 6 % on STREAM. Measuring several runs per job would lower it, at about 5 minutes of GPU time per run.

The tracked loops' baseline pools 5 runs taken 10 minutes apart from one clean build; it records its commit and the runs' times. To refresh a baseline, run `autan-bench stream` on an idle Spark from a clean checkout of `main`, promote it with `autan-bench baseline`, and commit the file with the reason in the pull request.
